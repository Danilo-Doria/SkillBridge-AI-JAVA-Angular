## Criterios de aceptación (validables por el coordinador)

1. El informe documenta, con rutas y líneas, la investigación previa: código de IA existente, fuentes de conocimiento reales y flujo elegido. **Si no hay caso de uso o fuentes que respalden una implementación segura y útil, se entrega solo el informe de bloqueo y no se escribe código de demostración.**
2. Existe un endpoint autenticado (propuesto `POST /api/ai/knowledge/ask`) que recibe una pregunta y devuelve respuesta + lista de fuentes (`sourceId`, título, fragmento, puntuación). Una respuesta sin evidencia suficiente devuelve explícitamente "sin información" y **no** invoca al LLM para inventar.
3. La respuesta solo usa fragmentos recuperados; cada afirmación se puede rastrear a una fuente listada.
4. Integración mediante puertos/adaptadores: el dominio sigue sin imports de framework; el controlador solo llama a un puerto de entrada; el acceso al LLM reutiliza el patrón de `AiRecommendationPort` o un puerto nuevo con adaptador en `infrastructure/adapter/out/`.
5. Validación y errores: pregunta vacía, mayor de N caracteres o sin autenticar → 400/401 con el formato de error existente (`GlobalExceptionHandler`); fallo o timeout del proveedor de IA → error controlado (sin trazas ni claves en la respuesta).
6. Seguridad: la recuperación nunca devuelve datos de otros usuarios (reservas, emails, pagos) ni ofertas inactivas; límite de longitud de entrada, número máximo de fragmentos y tamaño de contexto; timeout configurable; sin secretos en logs.
7. Pruebas unitarias del fragmentador/recuperador/ensamblador de prompt, prueba de capa web (MockMvc) y un recorrido funcional de extremo a extremo **con un doble determinista del LLM** (pregunta → recuperación → respuesta con fuentes; pregunta fuera de dominio → "sin información"). Ninguna prueba requiere claves reales ni red.
8. `mvn test` en `backend/` ejecutado en el worktree con resultado real informado; las pruebas que requieran Docker se declaran como no ejecutadas si no hubo daemon.
9. Ningún cambio fuera del alcance; sin dependencias de pago ni infraestructura vectorial nueva salvo justificación escrita aprobada por el coordinador (ver "Restricciones").
10. Informe final con el formato indicado.

## Caso de uso y usuario (hipótesis a validar, no a asumir)

Un CUSTOMER autenticado pregunta cómo funciona la plataforma o qué servicio encaja con una necesidad ("¿cuál es la política de cancelación?", "¿qué mentorías de Java hay?") y obtiene una respuesta con referencias. El agente debe **confirmar o refutar** esta hipótesis con la investigación; puede proponer una alternativa mejor respaldada por las fuentes reales.

## Diseño que debe quedar especificado en el informe y en el código

- **Ingestión/actualización**: de dónde se leen los documentos, cuándo se reindexa (arranque, programada o por evento), cómo se evita servir contenido obsoleto, cómo se excluye lo no público.
- **Fragmentación**: criterio (por sección/oferta), tamaño y solapamiento, metadatos (`sourceId`, tipo, título, URL/ruta).
- **Recuperación**: algoritmo elegido, `topK`, umbral mínimo de relevancia, desempate determinista.
- **Embeddings** (solo si se justifican): proveedor reutilizando credenciales ya soportadas, dimensión, almacenamiento; el modo por defecto debe funcionar **sin** embeddings remotos.
- **Generación**: prompt con instrucciones de responder solo con el contexto y citar fuentes; tratamiento del contexto recuperado como datos no confiables (mitigar prompt injection desde contenido de ofertas redactado por proveedores); validación de que las fuentes citadas existen entre las recuperadas.
- **Contrato de API**: esquema de petición/respuesta, códigos HTTP, límites (longitud de pregunta, p. ej. ≤ 500 caracteres; ≤ 5 fragmentos; contexto ≤ 6.000 caracteres; timeout del LLM configurable, p. ej. 15 s), correlación (`X-Correlation-Id`) y eventos de auditoría si se reutiliza `AuditEventPublisherPort`.
- **Consumo**: límite por usuario/ventana si es viable sin infraestructura nueva (el rate limiting global es SEC-010 y está fuera de alcance; documentar la brecha).

## Pruebas necesarias

- Unitarias: fragmentación (límites, solapamiento, vacío), ranking/umbral/desempate, construcción de prompt (incluye caso de contenido malicioso en una oferta), validación de fuentes citadas.
- Capa web: autenticado vs. anónimo, pregunta vacía/demasiado larga, "sin información", error y timeout del proveedor.
- Extremo a extremo (sin red): corpus fixture → pregunta en dominio → respuesta con fuentes correctas; pregunta fuera de dominio → "sin información" y **cero** llamadas al LLM doble; una oferta inactiva o ajena nunca aparece.
- Informar `mvn test` real (totales) y listar lo no ejecutado.

## Riesgos y pendientes conocidos

- Corpus pequeño (datos semilla mínimos): la utilidad puede ser limitada; reportar con honestidad.
- Contenido de proveedores = entrada no confiable (inyección de prompt).
- Pruebas de contexto Spring pueden requerir Docker (Testcontainers); preferir pruebas sin contexto completo.
- Latencia y coste de LLM no medibles sin claves; declararlo.
